## Порядок и зависимости

`P-01` и `P-02` задают корректный маршрут и wire-format. `P-03` зависит от них, чтобы измерять usage именно у выбранного backend. `P-04` можно выполнять параллельно с `P-02` после `P-01`, но изменения общих модулей сливать последовательно. `P-05` и `P-06` не входят в ближайший релиз без закрепленной версии backend, воспроизводимого сценария клиента и владельца тестового окружения. `P-07` закрывает только реально начатые задачи.

## Внедрение, совместимость и откат

Для P-01—P-04 использовать сначала тесты и исправления без изменения публичных DTO. Если новая проверка начнет отклонять ранее принимаемый запрос, задокументировать точный `param`, модель и способ исправления deployment до выпуска. Обновлять capabilities и catalog атомарно через существующий revision-based onboarding; сохранять прежний snapshot для возврата. При откате кода восстановить соответствующую ревизию конфигурации, иначе старые бинарники могут увидеть новые capabilities. Тарифы и ключи в рамках этого плана не меняются.

P-05 и P-06 включаются только для отдельных deployment. Сначала test environment, затем ограниченный canary, затем общий rollout при подтвержденных error rate, latency, empty/partial stream, usage и cost. Откат — выключить новый deployment/profile или вернуть предыдущую ревизию и направить model group на проверенный endpoint; уже выданные SSE chunks не переигрывать. Не удалять новые/старые deployment автоматически.

## Риски и решения до реализации

- Версии Azure API, Foundry project и vLLM могут различаться по инструментам, streaming usage и параметрам. Нужны закрепленные endpoint/version и набор контрактных ответов. Без них соответствующие возможности остаются «не подтверждено».
- У некоторых Ollama моделей reasoning расходует весь короткий output budget до видимого ответа. Это свойство модели и заданного лимита; Gateway должен честно возвращать `length` и usage. Менять default `think` для всех моделей нельзя без отдельного продукта/клиентского решения.
- Универсальный совместимый адаптер может принимать параметры, которые конкретный сервер игнорирует. Новые профили должны fail closed для явно неподдерживаемых семантических опций, сохраняя обратную совместимость для остальных deployment.
- Сетевые integration tests с облачными credentials не запускаются в обычном CI. Обязательная база CI — локальные `httptest` и PostgreSQL; opt-in cloud/backend smoke запускается с отдельными тестовыми credentials, не в логах и не в фикстурах.
- Разрешение на новые native операции, их тарифы и публичные API требуют отдельного бизнес-решения. В этот план они автоматически не входят.
